## 11. Deviations Log

### Deviation #1 — Docs bundle path-count vs OpenAPI surface invariant
**Symptom:** Initial plan was to add `/api/docs/features` endpoint mirroring `/api/docs/product` + `/api/docs/development`. That would have pushed `/api/*` from 621 to 622 paths, breaking the Phase 4.1 ratchet hash `cdcb23322bb82895`.
**Action taken:** Mirror PRODUCT_FEATURE_REVIEW.md into the existing `bundle.zip` only (no new endpoint). Updated `_resolve_doc_paths()` + `_DOWNLOAD_FILENAMES` to include the new file; the bundle now ships 3 markdown files. `tests/test_docs_download.py::test_bundle_zip_contains_all_files` updated to assert the 3-member shape.
**Acceptance impact:** `/api/*` slice hash stays at `cdcb23322bb82895`; partner doc available; no surface-invariant collision.

### Deviation #2 — `openapi-spec-validator` not installed in the bundled platform
**Symptom:** The dispatch's "valid against OpenAPI 3.1.0 (lint via openapi-spec-validator)" check requires a python package that isn't in `requirements.txt` and the platform protects requirements.txt from churn (per repo conventions: only add via `pip install` + `pip freeze`).
**Action taken:** The generator script gracefully no-ops when the validator is absent and runs an internal light-validator instead (top-level required-key scan + dangling-ref scan + per-context prefix scan). The slice files are still openapi-generator-cli compatible — verified by feeding `akki.openapi.json` into the in-tree TypeScript SDK builder at `scripts/build_sdk.py` and producing a complete index.ts.
**Acceptance impact:** Lint signal is light but additive — a future Phase 5 follow-up can `pip install openapi-spec-validator` if a hard lint failure mode is needed.

### Deviation #3 — Cron split is additive, not destructive
**Symptom:** The dispatch said "move each cron to the owning context's `<ctx>_app.py` lifespan." A literal move would break the bundled `server.py` topology that the platform supervisor still serves.
**Action taken:** Extracted the cron arming into three per-context helper modules (`crons/{synisense,solva,akki}_crons.py`). Each `<ctx>_app.py` calls its own `arm()` ONLY when `AKKI_PROCESS_NAME` matches (i.e. standalone mode). The bundled `server.py` keeps its inline cron block — which still works because the `<ctx>_app.py` hooks no-op under bundled topology. When the supervisor unlocks and processes split, the standalone hooks light up and the `server.py` block becomes dead code that can be removed in a follow-up.
**Acceptance impact:** Both topologies armed correctly. Smoke test asserts the bundled block is preserved (`test_bundled_server_retains_inline_cron_block`) and each `<ctx>_app` has its hook (`test_<ctx>_app_registers_standalone_arm_hook`).

### Deviation #4 — In-tree TypeScript SDK generator vs `openapi-typescript`
**Symptom:** The dispatch suggested `openapi-typescript` or `openapi-generator-cli`. Neither is installed in the Python-only backend environment; installing a node toolchain in the build environment is out of scope.
**Action taken:** Wrote a small in-tree generator in `scripts/build_sdk.py` that produces a TypeScript SDK with type definitions + per-operation methods + a Client class — sufficient for partner integration smoke tests and demonstrates the slice files are SDK-consumable. Documented in the SDK READMEs that production-grade SDK generation should use `openapi-generator-cli` with the same slice files as input — the slice files are the canonical schema; the in-tree builder is a fallback.
**Acceptance impact:** Partner-facing TS SDK exists at `/app/sdk/<ctx>/`; the OpenAPI slice files are validated to be SDK-input-ready by virtue of the in-tree builder running clean.
