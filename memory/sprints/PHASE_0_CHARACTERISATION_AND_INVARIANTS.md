## Notable design decisions

### Tenancy invariant — observe-mode + AST scan
The scanner walks `backend/services/` + `backend/routers/`, finds every direct call of shape `db.<collection>.<method>(...)`, and checks the filter (or document) Dict literal for an `account_id` key. Reports a single JSON file at `/app/memory/invariants/tenancy_violations.json` with rich shape (per-violation file:line + collection + method + kind).

**Tenant-scoped allow-list seeded with ~45 collections.** Deliberately excluded:
- `accounts` — the row IS the tenant (queries by `id` ARE tenant scope).
- `memberships` — link table; both `account_id`-filtered and `context_id`-filtered queries are legitimate; static classification unsafe.
- Admin / shared / cron-scoped collections (`synisense_audit_log`, `synisense_trust_receipts`, `news_articles`, `scheduler_locks`, etc.) — not tenant-scoped by design.

The full canonical list is a Phase 1 Pre-Read deliverable — flagged TODO in the file.

**Escape-hatch marker:** lines carrying the comment `# tenancy:allow-no-account-id` (on the call line OR the immediately-preceding line) are excluded. Reviewers use this for legitimate superadmin observability queries.

### Fail-closed invariant — exact monkeypatch target
The chat sync handler (`routers/chat.py:1738-1769`) imports `mint_chat_outcome` from `services.synisense.shield.canonical` INSIDE the function and catches `ShieldFailure` at the route boundary → HTTPException 503 with body `{"error": "shield_unavailable", ...}`. The invariant monkeypatches `services.synisense.shield.canonical.mint_chat_outcome` at the module level so any inline `from … import …` picks up the synthetic exploder.

First attempt patched `services.synisense.adapter.shield_payload_async` — INSUFFICIENT, because the chat router uses the canonical `mint_chat_outcome` mint pathway on the sync handler. Documented in the file's comments for future maintainers.

### Characterisation goldens — structural-shape strategy
LLM responses are non-deterministic — content goldens would be brittle. The implementation snapshots STRUCTURAL shape only:
- Field presence + type (str / int / float / bool / list / dict).
- Dynamic fields (audit_id, created_at, request_hash, etc.) collapse to `<dynamic>:<typename>`.
- First-run blesses the golden; subsequent runs compare top-level key sets.

If the response envelope changes (e.g. a field is removed), the test fails and the developer must explicitly re-bless via the documented procedure (delete the .golden.json, re-run). The re-bless is intentional friction.

### Shield-no-leak invariant — parametrised, not god-test
Two parametrised cases in Phase 0: chat surface + Solva analyze surface. Each surfaces a discrete fixture and asserts `[[ENT_` doesn't appear in the final user-visible payload.

The Work Studio compile / brief / pulse-idea surfaces are LOGGED as TODOs at the bottom of the file rather than half-implemented. Each new surface requires a working fixture (seeded context + source docs); Phase 0 ships the two surfaces with cheap synthetic-input fixtures, additions follow as fixture cost drops.

The Phase 14 file `test_chat_fluency_no_shield_leak.py` REMAINS as the chat-specific lockdown — they exercise the same prompt fixture.

## Deviations from the dispatch brief

**None material.** Two minor implementation choices documented above:

1. **Tenancy allow-list excludes `accounts` + `memberships`.** The dispatch said "seeded with the obvious candidates ... etc." and explicitly called for a TODO for Phase 1 confirmation. Excluding these two prevents false-positive flooding of the report on legitimate primary-key queries; TODO comment in the file documents the rationale.

2. **Characterisation goldens use first-run blessing.** First execution writes the golden; subsequent runs compare. The dispatch did not specify the blessing mechanism, but this approach is the standard for golden-file testing and avoids the chicken-and-egg of "commit a golden before the test exists".
